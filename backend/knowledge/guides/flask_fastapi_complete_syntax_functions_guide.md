# PART I — WEB FRAMEWORK FOUNDATIONS

# 1. Flask vs FastAPI

| Feature | Flask | FastAPI |
|---|---|---|
| Core style | Lightweight WSGI web framework | ASGI API framework built on Starlette and Pydantic |
| Main strength | Flexible web apps, templates, small-to-large apps using extensions | Typed API endpoints, validation, OpenAPI docs, async-friendly I/O |
| Input validation | Usually explicit or added by extensions | Automatic validation/serialization from type declarations and Pydantic |
| API documentation | Add an extension/library if desired | OpenAPI schema and interactive docs generated by default |
| HTML templates | Built-in integration with Jinja | Can use Starlette/Jinja integration, but not the primary focus |
| Async model | Async views are supported, but Flask remains WSGI-based | ASGI-first; supports `async def` endpoints and async dependencies |
| Database | Bring your preferred library/extension | Bring your preferred driver/ORM |
| Ideal uses | HTML websites, small services, flexible server-side apps | REST APIs, data/ML inference APIs, typed backend services |

Choose based on your project. You do not need to use both in the same application. If one project uses Flask and another uses FastAPI, keep their dependency environments clear.

# 4. HTTP and REST Fundamentals

A backend handles HTTP requests and returns HTTP responses.

Request components:
- Method: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, etc.
- Path: `/api/products/12`
- Query string: `?page=2&limit=20`
- Headers: `Content-Type`, `Authorization`, `Accept`, etc.
- Body: commonly JSON for REST APIs, or form/multipart data.

Common status codes:

| Code | Use |
|---:|---|
| `200` | Successful request |
| `201` | Resource created |
| `202` | Accepted for asynchronous processing |
| `204` | Success with no response body |
| `400` | Invalid request |
| `401` | Authentication missing/invalid |
| `403` | Caller is not permitted |
| `404` | Resource not found |
| `409` | Conflict, e.g. duplicate unique value |
| `413` | Request/entity too large |
| `415` | Unsupported media type |
| `422` | Often used for syntactically valid but semantically invalid data; framework conventions vary |
| `429` | Rate limit exceeded |
| `500` | Unexpected server error |
| `502` / `503` / `504` | Gateway/upstream/service availability/timeouts |

REST is a design style rather than a strict Python feature. Use resource-oriented URLs, clear method semantics, stable response schemas, validation, and consistent errors.

# 5. Environment Variables and Configuration

Never hard-code production passwords, API keys, JWT signing keys, or database connection secrets.

Example `.env` for local development (do not commit a real secret):

```dotenv
APP_ENV=development
DATABASE_URL=postgresql://user:password@localhost:5432/appdb
API_KEY=replace-with-a-local-placeholder
```

Python access:

```python
import os

database_url = os.environ.get("DATABASE_URL")
if not database_url:
    raise RuntimeError("DATABASE_URL is required")
```

Loading `.env` files generally uses an additional package such as `python-dotenv` or a project-specific settings layer. Production should use an orchestrator or secrets manager, and you should understand how configuration is loaded and overridden.

Keep separate configuration for development, tests, and production. Do not expose debug mode, detailed stack traces, or developer reloaders to the public production service.

# 6. JSON, Status Codes, Headers, Cookies, and CORS

JSON is the common API interchange format.

Request header:

```http
Content-Type: application/json
Accept: application/json
```

Typical JSON body:

```json
{
  "name": "Keyboard",
  "price": 2499.00
}
```

Response metadata includes a status code, headers, and possibly a body.

Cookies may contain session identifiers; configure `Secure`, `HttpOnly`, and `SameSite` appropriately when applicable. Do not put passwords or long-lived credentials in ordinary browser-readable cookies.

**CORS** is a browser policy governing whether JavaScript running on one origin can read a response from another. CORS is not authentication, and it is not a firewall for non-browser clients.

# 8. Routes and URL Rules

Basic route:

```python
@app.route("/products", methods=["GET"])
def list_products():
    return {"items": []}
```

Convenience decorators:

```python
@app.get("/products")
def get_products():
    return {"items": []}

@app.post("/products")
def create_product():
    return {"created": True}, 201
```

Path converters:

```python
@app.get("/users/<int:user_id>")
def get_user(user_id: int):
    return {"user_id": user_id}

@app.get("/files/<path:filename>")
def get_file(filename: str):
    return {"requested_file": filename}
```

Common converters include `string`, `int`, `float`, `path`, and `uuid` (depending on Flask/Werkzeug version). A `path` converter can match slashes, so be careful when accepting file-like paths.

Route rules:
- Route patterns should be unambiguous.
- Use meaningful names for endpoints.
- Prefer explicit methods.
- Avoid side effects in `GET` endpoints.
- Validate identifiers and authorize access to the resource.
- Do not assume that a hidden frontend link protects the backend.

# 9. Path, Query, Form, and JSON Parameters

## Path parameter

```python
@app.get("/products/<int:product_id>")
def get_product(product_id):
    return {"product_id": product_id}
```

## Query parameter

```python
from flask import request

@app.get("/products")
def list_products():
    page = request.args.get("page", default=1, type=int)
    limit = request.args.get("limit", default=20, type=int)
    return {"page": page, "limit": limit}
```

Validate bounds; `type=int` handles simple conversion but does not enforce a safe positive limit.

## Form data

```python
@app.post("/login")
def login():
    username = request.form.get("username", "")
    return {"username_received": bool(username)}
```

Don't return passwords or authentication secrets.

## JSON body

```python
from flask import request

@app.post("/api/products")
def create_product():
    data = request.get_json()
    if not isinstance(data, dict):
        return {"error": "Expected a JSON object"}, 400

    name = data.get("name")
    price = data.get("price")
    if not isinstance(name, str) or not name.strip():
        return {"error": "name is required"}, 400

    return {"name": name.strip(), "price": price}, 201
```

This example demonstrates the framework shape, not complete production validation. Add schema validation, type checks, business rules, and authorization for real applications. Flask does not automatically validate arbitrary JSON fields like FastAPI/Pydantic does.

# 10. Requests and Responses

Flask's common request/response APIs include:
- `request.method`
- `request.path`
- `request.full_path`
- `request.args`
- `request.form`
- `request.files`
- `request.headers`
- `request.cookies`
- `request.get_json(...)`
- `request.is_json`
- `request.remote_addr` (may be influenced by proxy setup; do not blindly trust it)
- `current_app`
- `g`

Return values can include strings, dictionaries/lists (JSON support depends on Flask version), response objects, or tuples with status/headers.

```python
from flask import jsonify, make_response

@app.get("/api/status")
def status():
    return jsonify({"status": "ok"})

@app.get("/api/custom")
def custom_response():
    response = make_response({"message": "created"}, 201)
    response.headers["X-App-Version"] = "1"
    return response
```

Redirect:

```python
from flask import redirect, url_for

@app.get("/go-home")
def go_home():
    return redirect(url_for("home"))
```

Avoid creating an open redirect from a user-supplied URL without validation.

# 11. Templates with Jinja

Flask integrates with Jinja templates. Template rendering is useful for server-rendered HTML.

```python
from flask import render_template

@app.get("/hello/<name>")
def hello(name):
    return render_template("hello.html", name=name)
```

`templates/hello.html`:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Hello</title>
</head>
<body>
  <h1>Hello, {{ name }}</h1>
</body>
</html>
```

Jinja basics:

```jinja2
{{ value }}
{{ user.name }}
{{ user["name"] }}

{% if user %}
  <p>Welcome</p>
{% else %}
  <p>Please sign in</p>
{% endif %}

{% for item in items %}
  <li>{{ item }}</li>
{% endfor %}
```

Template inheritance:

```jinja2
{# base.html #}
<!doctype html>
<html lang="en">
<body>
  <main>{% block content %}{% endblock %}</main>
</body>
</html>
```

```jinja2
{# page.html #}
{% extends "base.html" %}
{% block content %}
  <h1>{{ title }}</h1>
{% endblock %}
```

Jinja commonly autoescapes HTML templates, but do not assume every context/file type is autoescaped in the same way. Avoid marking untrusted content `safe`; escaping does not replace output-context-aware security practices.

# 13. Redirects, URL Building, and Flash Messages

`url_for` builds a URL from an endpoint and arguments:

```python
url_for("get_user", user_id=42)
```

Flashing a short message into the next request:

```python
from flask import flash, redirect, render_template, url_for

@app.post("/save")
def save():
    # Persist validated data here.
    flash("Saved successfully", "success")
    return redirect(url_for("home"))
```

Template:

```jinja2
{% with messages = get_flashed_messages(with_categories=true) %}
  {% for category, message in messages %}
    <div class="alert alert-{{ category }}">{{ message }}</div>
  {% endfor %}
{% endwith %}
```

Flashed messages depend on session configuration; set a secure secret key and cookie settings. Do not display sensitive internal exceptions in flash messages.

# 14. Application and Request Context

Important Flask context objects:
- `current_app`: current application proxy.
- `request`: current request proxy.
- `session`: session data proxy.
- `g`: request/application-context scoped storage, commonly used for request-local resources.

Example:

```python
from flask import g

@app.before_request
def load_request_marker():
    g.request_marker = "active"

@app.get("/marker")
def marker():
    return {"marker": g.request_marker}
```

Context values should not be treated as durable storage across requests. Put persistence in an actual database/cache, not `g`.

Application context example:

```python
with app.app_context():
    print(app.config["DEBUG"])
```

Request context behavior and lifetime are documented in Flask's context reference. Accessing `request` outside a request context typically raises a context-related runtime error.

# 15. Configuration and Application Factories

Flask configuration is accessible through `app.config`.

```python
app.config.update(
    TESTING=False,
    DEBUG=False,
    JSON_SORT_KEYS=False
)
```

Configuration settings are version-dependent; use documented config keys for the installed Flask release.

Application factory pattern:

```python
from flask import Flask

def create_app(test_config=None):
    app = Flask(__name__)
    app.config.from_mapping(
        SECRET_KEY=None,
        DATABASE_URL=None
    )

    if test_config is not None:
        app.config.update(test_config)

    # Register extensions/blueprints here.
    return app
```

A production deployment must provide a sufficiently random secret key. Avoid shipping a default known key.

Factory benefits:
- Easier testing with isolated app instances
- Multiple configuration sets
- Cleaner extension/blueprint initialization
- Reduced import-time side effects

# 16. Blueprints and Modular Routing

Blueprints group routes and related behavior.

`products/routes.py`:

```python
from flask import Blueprint, jsonify

products_bp = Blueprint("products", __name__, url_prefix="/api/products")

@products_bp.get("/")
def list_products():
    return jsonify({"items": []})

@products_bp.get("/<int:product_id>")
def get_product(product_id):
    return {"id": product_id}
```

Register:

```python
from flask import Flask
from products.routes import products_bp

def create_app():
    app = Flask(__name__)
    app.register_blueprint(products_bp)
    return app
```

Blueprints can have URL prefixes, subdomains, template/static settings, error handlers, request hooks, and CLI commands, subject to Flask's documented API. They are not separate app instances; they are registered onto an application.

# 17. Error Handling

Return appropriate status codes for expected client errors and use centralized handlers for consistent error bodies.

```python
from flask import jsonify

@app.errorhandler(404)
def not_found(error):
    return jsonify({"error": "Not found"}), 404

@app.errorhandler(500)
def internal_error(error):
    app.logger.exception("Unexpected server error")
    return jsonify({"error": "Internal server error"}), 500
```

Custom exception:

```python
class ProductNotFoundError(Exception):
    pass

@app.errorhandler(ProductNotFoundError)
def handle_product_not_found(error):
    return {"error": str(error)}, 404
```

Avoid leaking stack traces, filesystem paths, SQL queries, access tokens, database credentials, or personal data to clients. Log diagnostic details securely on the server with a request/correlation ID if useful.

Error handlers can be registered for status codes or exception classes. Blueprint-level and application-level error behavior has ordering/scope details; consult Flask docs.

# 18. Hooks and Request Lifecycle

Common Flask hooks:
- `before_request`
- `after_request`
- `teardown_request`
- `before_app_request` / related Blueprint hooks
- `context_processor`
- Template filters and tests
- Signals (with their documented caveats)

Examples:

```python
@app.before_request
def before():
    # Authenticate/prepare only what is appropriate here.
    pass

@app.after_request
def add_header(response):
    response.headers.setdefault("X-Content-Type-Options", "nosniff")
    return response

@app.teardown_request
def cleanup(error=None):
    # Release request-local resources if your integration requires it.
    pass
```

`after_request` handlers receive a response and must return it. Teardown hooks are for cleanup and should not assume that a request succeeded. Avoid repeating expensive global work on every request.

# 19. Sessions and Cookies

Flask's default session interface stores signed session data in a cookie. A signature provides integrity, not confidentiality: users may be able to inspect session contents. Do not place passwords or sensitive secrets in the default client-side session.

Set cookie/session settings intentionally:

```python
app.config.update(
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SECURE=True,   # HTTPS deployment
    SESSION_COOKIE_SAMESITE="Lax"
)
```

Configure a strong secret key through a secret manager/environment:

```python
import os
app.config["SECRET_KEY"] = os.environ["FLASK_SECRET_KEY"]
```

Login/session security may require CSRF protection, session rotation after authentication, expiration controls, secure logout, and server-side session storage depending on the threat model. Flask's default signed session is not equivalent to a revocable server-side session store.

# 21. Async Views and Background Work

Flask supports `async def` views when installed/configured according to the documented async support. Flask remains a WSGI framework: async views do not automatically make all request processing non-blocking or improve throughput for every workload.

Example shape:

```python
@app.get("/async-info")
async def async_info():
    result = await some_async_operation()
    return {"result": result}
```

`some_async_operation` must be a genuine awaitable async function from an appropriate library; calling blocking I/O inside an async view still blocks the execution context.

For long-running/durable tasks, use a task queue such as Celery/RQ or a managed worker system when appropriate. A short in-process background task is not the same as durable job processing; it may be lost if the process exits.

# 22. Flask Extensions and Database Integration

Flask is intentionally small and relies on libraries/extensions for optional behavior.

Common extension categories:
- Database/ORM integrations (e.g., Flask-SQLAlchemy)
- Migrations (e.g., Flask-Migrate/Alembic)
- Authentication/session management
- CSRF protection and form validation
- Rate limiting
- Caching
- Mail
- REST/API serialization

For SQLAlchemy-style database access, use parameterized ORM/core expressions rather than concatenating input into SQL. Manage sessions/connections in the application's lifecycle and clean them up properly.

Flask does not itself require a particular SQL database or ORM. SQLite is useful for small local examples; PostgreSQL/MySQL/SQL Server may be appropriate for deployed applications depending on requirements.

# 23. Testing Flask Applications

Flask's test client can make in-process requests without running a public server.

```python
import pytest
from app import create_app

@pytest.fixture()
def app():
    return create_app({"TESTING": True, "SECRET_KEY": "test-only-key"})

@pytest.fixture()
def client(app):
    return app.test_client()

def test_home(client):
    response = client.get("/")
    assert response.status_code == 200
```

JSON request:

```python
def test_create_product(client):
    response = client.post(
        "/api/products",
        json={"name": "Keyboard", "price": 100}
    )
    assert response.status_code in (200, 201)
```

The accepted status above depends on the actual route implementation; in a real test assert the contractually expected status exactly.

Test:
- Successful responses
- Validation failures
- Authentication/authorization
- Not-found cases
- Database transactions and rollback
- Malformed JSON/form submissions
- Upload limits
- Error handlers
- Session/CSRF behavior
- Application factory with test configuration

Use isolated test data and do not let unit/integration tests modify production databases.

# 24. Logging, Debugging, and Production Deployment

Flask exposes an app logger:

```python
app.logger.info("Request completed")
app.logger.warning("Unexpected input")
app.logger.exception("Operation failed")
```

Useful practices:
- Use the standard logging module.
- Avoid `print` for production diagnostics.
- Do not log passwords, authorization headers, session IDs, or raw sensitive payloads.
- Add request IDs and useful structured context if available.
- Keep debug mode and interactive debugger off in production.
- Use a supported WSGI server or hosting configuration.
- Set reverse-proxy headers securely if behind a proxy, and trust only known proxy hops.
- Terminate TLS appropriately.
- Configure process supervision and graceful shutdown.
- Keep dependencies patched and secrets externalized.
- Run migrations safely during deployment.
- Set request body limits and timeouts.

The right production server and concurrency model depend on platform and workload. Follow Flask's official deployment instructions for the actual hosting environment.

# 26. Path Operations and HTTP Methods

A FastAPI endpoint is often called a path operation function.

```python
from fastapi import FastAPI, status

app = FastAPI()

@app.get("/items")
def list_items():
    return []

@app.post("/items", status_code=status.HTTP_201_CREATED)
def create_item():
    return {"created": True}

@app.put("/items/{item_id}")
def replace_item(item_id: int):
    return {"item_id": item_id, "replaced": True}

@app.patch("/items/{item_id}")
def update_item(item_id: int):
    return {"item_id": item_id, "updated": True}

@app.delete("/items/{item_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_item(item_id: int):
    return None
```

Common decorators:
- `@app.get`
- `@app.post`
- `@app.put`
- `@app.patch`
- `@app.delete`
- `@app.options`
- `@app.head`
- `@app.api_route` for multiple methods/custom operation definitions
- `@app.websocket` for WebSocket endpoints

`status.HTTP_*` constants are provided by Starlette/FastAPI integrations. Choose response codes consistent with API semantics. A `204` response must not carry a normal response body.

# 27. Path, Query, Header, Cookie, and Body Parameters

FastAPI uses type annotations and parameter declarations to infer request parameter sources.

## Path parameters

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

A non-integer value for `user_id` will fail validation rather than silently becoming an arbitrary string.

## Query parameters

```python
@app.get("/items")
def list_items(skip: int = 0, limit: int = 20):
    return {"skip": skip, "limit": limit}
```

Optional parameters:

```python
def search(q: str | None = None):
    return {"q": q}
```

Set bounds:

```python
from typing import Annotated
from fastapi import Query

@app.get("/search")
def search_items(
    q: Annotated[str | None, Query(max_length=100)] = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 20
):
    return {"q": q, "limit": limit}
```

## Path metadata and constraints

```python
from fastapi import Path

@app.get("/items/{item_id}")
def get_item(item_id: Annotated[int, Path(gt=0)]):
    return {"item_id": item_id}
```

## Headers

```python
from fastapi import Header

@app.get("/client")
def client_info(user_agent: Annotated[str | None, Header()] = None):
    return {"user_agent": user_agent}
```

## Cookies

```python
from fastapi import Cookie

@app.get("/preferences")
def preferences(theme: Annotated[str | None, Cookie()] = None):
```

```python
from pydantic import BaseModel
```

# 28. Pydantic Models and Validation

Pydantic models define structured data, validation, and serialization behavior.

```python
from pydantic import BaseModel, Field, EmailStr

class UserCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    email: EmailStr
    age: int | None = Field(default=None, ge=0, le=130)
```

Use email validation only after installing the optional dependency required by the chosen Pydantic version (commonly `email-validator`).

Nested models:

```python
class Address(BaseModel):
    city: str
    country: str

class UserCreate(BaseModel):
    name: str
    address: Address
    tags: list[str] = []
```

For mutable field defaults, Pydantic typically handles data model defaults safely through its model semantics, but understand the validation library's documented behavior. For plain Python classes, use `default_factory` for mutable defaults.

Field aliases, strictness, validators, model validators, custom serializers, computed fields, and configuration options are supported by Pydantic; exact decorators/options depend on the Pydantic version.

Example custom validation with a field validator (Pydantic v2):

```python
from pydantic import BaseModel, field_validator

class UsernameInput(BaseModel):
    username: str

    @field_validator("username")
    @classmethod
    def normalize_username(cls, value: str) -> str:
        value = value.strip()
        if not value:
            raise ValueError("username cannot be empty")
        return value
```

Use validation for input shape/rules, but check resource ownership, permissions, and business constraints in the application/service layer.

# 30. Dependencies and Dependency Injection

FastAPI's `Depends` lets endpoints share setup logic, database sessions, authentication, or reusable parameter validation.

```python
from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()

def common_parameters(skip: int = 0, limit: int = 20):

CommonParams = Annotated[dict, Depends(common_parameters)]

@app.get("/items")
def list_items(params: CommonParams):

```

Real code generally uses typed models/services rather than a loosely typed dictionary.

```python
def get_resource():

    try:
        yield resource
    finally:
        resource.close()
```

```python
ResourceDep = Annotated[Resource, Depends(get_resource)]
```

- `Depends(...)`
- `Security(...)` for security-aware dependencies/scopes

- Dependency overrides in tests

- `yield` dependencies for setup/cleanup
- Scope/lifetime options where supported by the installed version

# 31. Error Handling

Raise `HTTPException` for expected API errors:

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def get_item(item_id: int):
    item = load_item(item_id)
    if item is None:
        raise HTTPException(status_code=404, detail="Item not found")
    return item
```

`load_item` is application-specific, not a built-in FastAPI function.

Custom exception handler:

```python
from fastapi import Request
from fastapi.responses import JSONResponse

class DomainConflict(Exception):
    pass

@app.exception_handler(DomainConflict)
async def domain_conflict_handler(request: Request, exc: DomainConflict):
    return JSONResponse(
        status_code=409,
        content={"detail": str(exc)}
    )
```

Do not return internal tracebacks, database passwords, SQL strings, or sensitive request payloads to API clients. Log diagnostic details safely and keep public error messages appropriately generic.

FastAPI/Pydantic validation errors have framework-defined response shapes. Avoid catching every `Exception` and converting it into a success response or hiding all diagnostic information.

# 32. Authentication and Security Schemes

FastAPI provides reusable security components integrated with OpenAPI.

Common tools include:
- `HTTPBasic`
- `HTTPBearer`
- `APIKeyHeader`
- `APIKeyQuery`
- `APIKeyCookie`
- OAuth2 utilities such as `OAuth2PasswordBearer`
- `Security` and `Depends`

Illustrative bearer-token extraction:

```python
from typing import Annotated
from fastapi import Depends, FastAPI
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

app = FastAPI()
bearer_scheme = HTTPBearer()

@app.get("/protected")
def protected(
    credentials: Annotated[HTTPAuthorizationCredentials, Depends(bearer_scheme)]
):
    # This example demonstrates extraction only.
    # Real code must validate token signature/issuer/audience/expiry and permissions.
    return {"scheme": credentials.scheme}
```

A security scheme does not by itself implement complete authentication. Use a well-reviewed identity provider or a correct framework integration. Do not manually trust a token because it is syntactically present.

Authentication = who the caller is. Authorization = whether the caller may perform this specific operation on this specific resource.

# 33. OAuth2/JWT Architecture (Integration Pattern)

A secure authentication design usually includes:
- Identity provider or trusted token issuer
- Login/token acquisition flow
- Token validation
- Claims/role/scope validation
- Expiration and key rotation
- Protected endpoints
- Revocation/refresh strategy where applicable
- Secure storage and transport

JWT validation must verify at least the required signature algorithm/key, issuer, audience, expiry/not-before rules, and application authorization claims. Do not decode the token payload and assume it is trusted.

Illustrative dependency shape:

```python
def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    payload = verify_token_with_trusted_library(token)
    user = load_user(payload["sub"])
    if user is None:
        raise HTTPException(status_code=401, detail="Invalid authentication")
    return user
```

`verify_token_with_trusted_library`, `load_user`, and `oauth2_scheme` configuration depend on the chosen identity/auth package and are not magic built-ins.

Protect sensitive routes with server-side checks. Avoid putting long-lived access tokens into local storage if the application's threat model makes them accessible to injected JavaScript; select a cookie/token storage pattern deliberately.

# 34. Middleware, CORS, and Lifespan

## Middleware

Middleware runs around request handling. Use it for cross-cutting concerns such as request IDs, timing, logging, and specific headers. Avoid turning middleware into a place for all business logic.

```python
from fastapi import FastAPI, Request
import time

app = FastAPI()

@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time"] = str(time.perf_counter() - start)
    return response
```

Middleware ordering matters. A middleware that errors before calling the next handler must return a valid response or raise a well-understood exception.

## CORS middleware

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
```

Use explicit trusted origins. Wildcard origins and credentialed requests need careful configuration. CORS is not authentication.

## Lifespan

Current FastAPI documentation recommends a lifespan context manager for startup/shutdown resource setup rather than relying on legacy event-handler patterns.

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Initialize shared resources here, such as a connection pool or model.
    app.state.ready = True
    yield
    # Close shared resources here.

app = FastAPI(lifespan=lifespan)
```

The example's `app.state.ready` is only illustrative. Close database clients and models according to their documented lifecycle rules, and make sure shutdown works cleanly.

# 35. Uploads, Downloads, Streaming, and Form Data

File uploads commonly use `UploadFile` and `File`; form fields use `Form`. Multipart parsing may require the optional `python-multipart` dependency.

```python
from typing import Annotated
from fastapi import FastAPI, File, UploadFile, HTTPException

app = FastAPI()

@app.post("/upload")
async def upload_file(file: UploadFile):
    if not file.filename:
        raise HTTPException(status_code=400, detail="Filename required")

    # Demonstration only. Validate size/content and store safely in production.
    first_bytes = await file.read(1024)
    await file.seek(0)

    return {
        "filename": file.filename,
        "content_type": file.content_type,
        "sample_bytes": len(first_bytes),
    }
```

Production upload requirements:
- Set size limits at proxy/server/application layers.
- Validate actual file content, not only the filename/MIME value supplied by client.
- Use server-generated storage identifiers.
- Avoid path traversal and overwriting files.
- Store outside publicly executable paths or in private object storage.
- Apply authentication/authorization and quotas.
- Consider malware scanning and data-retention requirements.

Download response classes include `FileResponse` and `StreamingResponse` where appropriate. Protect access to private files and set safe headers. Do not expose arbitrary filesystem paths as route parameters.

# 36. Background Tasks

Small in-process work after the response:

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

def write_audit_entry(message: str) -> None:
    # Example only; real code writes through a safe logger/storage service.
    print(message)

@app.post("/events", status_code=202)
def create_event(background_tasks: BackgroundTasks):
    background_tasks.add_task(write_audit_entry, "event accepted")
    return {"accepted": True}
```

`BackgroundTasks` is not a durable distributed job queue. For heavy computation, retries, long jobs, or workloads that must survive process restarts, use an external task queue/worker system and persist job state.

Background-task functions should catch/report failures, respect privacy, and not depend on request-scoped objects after their valid lifetime.

# 39. Database Integration

FastAPI does not force a particular database. Typical choices include:
- Relational: PostgreSQL, MySQL, SQLite, SQL Server
- Document: MongoDB
- Redis or another cache
- Vector storage appropriate to the chosen system

For SQL databases, use a driver/ORM such as SQLAlchemy or a supported database client. Use parameterized statements and transactions. For MongoDB, use the official driver or a documented ODM. Do not share one session/connection object unsafely across concurrent requests.

A dependency can provide a resource per request:

```python
def get_database_session():
    session = create_session()
    try:
        yield session
    finally:
        session.close()
```

`create_session` and `session` are placeholders for your chosen database library. Configure pool limits, timeouts, transaction boundaries, and startup/shutdown lifecycle based on that library's official guidance.

Never:
- Build SQL with string concatenation from user inputs.
- Let public clients choose unrestricted collection/table names.
- Return full database records containing secrets by default.
- Keep database transactions open while making slow remote model/API calls unless there is a carefully designed reason.

# 40. Async, Concurrency, and External HTTP Calls

FastAPI supports `async def` endpoints and ordinary `def` endpoints. Use `async def` when the awaited operations are asynchronous and non-blocking; blocking code can still block the event loop.

Async HTTP example:

```python
import httpx
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/external-status")
async def external_status():
    try:
        async with httpx.AsyncClient(timeout=5.0) as client:
            response = await client.get("https://example.com/status")
            response.raise_for_status()
            return {"status_code": response.status_code}
    except httpx.HTTPError:
        raise HTTPException(status_code=502, detail="Upstream service failed")
```

For a high-throughput app, consider reusing a client through application lifespan rather than creating a new client for every request, and close it cleanly. This minimal example uses a per-request client for simplicity.

Concurrency notes:
- Async is useful for high-volume I/O when the dependencies are async.
- Sync endpoints run according to the framework/server's threadpool execution strategy.
- CPU-heavy AI inference can block the event loop if run directly there; use an appropriate worker/process/GPU serving arrangement.
- Apply timeouts, connection limits, cancellation, and retry rules.
- Do not retry non-idempotent operations blindly.

# 46. MongoDB Integration Patterns

For MongoDB, design collections around query and update patterns:
- Choose stable IDs.
- Decide embedding versus referencing.
- Create indexes for expected query shapes.
- Add collection validators for important structural rules.
- Use atomic single-document operations where possible.
- Use transactions only when multi-document atomicity is needed.

- Use a long-lived client/connection pool.

# 47. AI/ML Model Serving with Flask or FastAPI

Frameworks are the HTTP layer; model inference is separate application logic.

A practical pattern:
1. Load/initialize the model at application startup/lifespan.
2. Validate request fields and request size.

4. Run inference with the framework's correct inference mode.

# 48. Security and Production Checklist

- Validate path, query, header, JSON, form, and file inputs.

- Use explicit output schemas.

## Deployment
- Disable debug mode/reloaders in production.
- Use HTTPS/TLS as required.
- Store secrets in environment/secret manager, not in Git.
- Patch dependencies and runtime.
- Restrict network exposure.
- Use least-privilege database/service accounts.
- Configure timeouts and graceful shutdown.
- Add health, metrics, and log redaction.
- Back up data and test restores.

# 49. Common Errors and Troubleshooting

| Symptom | Areas to inspect |
|---|---|
| Import error | Virtual environment, installed package version, import path |
| Flask route returns 404 | Registered route, URL prefix, method, blueprint registration |
| FastAPI validation error | Path/query/body types, Pydantic schema, request JSON |
| 405 Method Not Allowed | Route exists but the HTTP method is not registered |
| 422 response | FastAPI input validation, required fields and constraints |
| 401/403 | Authentication configuration vs permission policy |
| CORS error in browser | Allowed origin/method/header configuration; not the same as server auth |
| Slow response | Database plan, blocking I/O, model initialization, upstream latency |
| Async endpoint blocks | Blocking library called directly from event-loop path |
| Database connection leak | Incorrect resource/session lifecycle |
| Duplicate write | Missing unique constraint/idempotency, retry behavior |

| Production crash | Logs, environment variables, worker/timeout/memory settings |
| Secret appears in logs | Redaction and logging configuration |
| Test suite depends on external service | Use a stub/mock or isolated integration environment |

Diagnose with a minimal reproducible case, exact framework/database versions, server logs, and a test that isolates the failing behavior. Do not paste secrets or personal data into bug reports.

# 51. Learning Roadmap and Practice Projects

Learning order:
1. Python functions, collections, exceptions, and modules.
2. HTTP, JSON, URLs, headers, status codes, cookies, and CORS.
3. Flask basics or FastAPI basics (start with one).
4. Route parameters and validation.
5. Service/repository structure.
6. SQL or MongoDB integration.
7. Authentication and authorization.
8. Tests and error handling.
9. Logging, configuration, and deployment.
10. AI inference integration only after reliable API foundations.

Practice projects:
- Health/status API
- Product CRUD API
- User accounts and preferences
- Anime catalog API with search/pagination
- File upload service with quotas and private storage
- Discussion API with role/ownership checks
- AI sentiment/classification endpoint
- RAG retrieval endpoint with source citations
- Background-job API with task status tracking
- Deployment-ready app with CI, tests, and monitoring

For every project, define a request/response contract, error format, security rules, test data, and deployment configuration.
